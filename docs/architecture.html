Données & multi-tenant

application/utils/db.py porte tout le stockage Postgres. Chaque table est scopée par client_id en plus de product_type : deux clients peuvent tous deux appeler leur catalogue "shop" sans collision, car la vraie clé de partition est (client_id, product_type). La clé API (hashée) est l'unique moyen de résoudre un client_id.

02

Content-based : TF-IDF + similarité sémantique

/getRec/content combine deux signaux plutôt qu'un seul : le TF-IDF capture le vocabulaire partagé, les embeddings sémantiques rattrapent les synopsis reformulés ou thématiquement proches sans mot commun. Les deux pools de candidats sont fusionnés (union), pas intersectés, pour ne perdre ni une forte correspondance sémantique seule, ni une forte correspondance TF-IDF seule.

get_cosine_similarities_cached()

Vectorise le "bag of words" (titre + description + genre) via CountVectorizer/TfidfVectorizer, mis en cache par (client_id, product_type) pour éviter de revectoriser à chaque requête.

find_similar_by_embedding()

Recherche de plus proches voisins en pgvector sur product_embeddings — même modèle d'embedding que celui utilisé à l'ingestion (all-MiniLM-L12-v2, 384 dimensions).

diversify_by_genre()

Corrige un mode de défaillance réel : un candidat peut scorer anormalement haut sur les deux signaux à cause d'une coïncidence textuelle isolée (ex. deux titres qui partagent une phrase sans rapport thématique) et écraser toute alternative pertinente du bon genre.

03

Collaboratif : implicit ALS

build_user_item_matrix() construit une matrice de confiance à partir des événements bruts — pas une note fabriquée de 1 à 5 : un achat pèse plus qu'une vue dans le feedback implicite qu'ALS entraîne et prédit.

04

Hybride & recommandations de session

/getRec/hybrid part du pool content-based puis y superpose le score ALS restreint aux mêmes candidats, combinés via alpha (poids collaboratif) réglable par requête ; si aucun modèle n'est encore entraîné pour ce client, l'endpoint dégrade proprement vers le contenu seul plutôt que d'échouer. /getRec/session et /getRec/sessionForUser partagent compute_session_recs() : recommandations pondérées par récence à partir des derniers produits consultés, sans compte requis pour la première, sourcées de l'historique persistant en base pour la seconde — les deux classent les résultats de façon identique.

normalize_scores()

Min-max normalise chaque signal indépendamment avant blend — nécessaire car un score cosinus TF-IDF et un score ALS ne vivent pas sur la même échelle.

compute_session_recs()

Pondère chaque produit récemment consulté par sa position dans la liste (le plus récent compte le plus), combine les similarités, puis applique la même diversification par genre.

05

Versioning & réentraînement automatique

train_and_maybe_promote_model() entraîne toujours un nouveau candidat, l'évalue sur un split tenu à l'écart, puis ne le promeut en production que s'il égale ou dépasse la precision@10 de la version actuellement active — un run rejeté reste enregistré dans l'historique plutôt que de disparaître. Le réentraînement automatique (maybe_trigger_auto_retrain) se déclenche quand le nombre d'interactions nouvelles depuis le dernier entraînement dépasse un seuil, plutôt que sur un cron aveugle sans notion de "y a-t-il un signal nouveau à apprendre".

  1. Détection du seuil

    Chaque événement purchase/view appelle maybe_trigger_auto_retrain() ; si les interactions nouvelles depuis le dernier entraînement dépassent AUTO_RETRAIN_INTERACTION_THRESHOLD = 50, un job est mis en file.

  2. Entraînement candidat

    Un nouveau modèle ALS est entraîné sur 100% des données disponibles ; sa precision@10 est mesurée séparément sur un split de validation.

  3. Décision de promotion

    Promu seulement si sa precision@10 égale ou dépasse la version active — sinon la version précédente continue d'être servie sans interruption.

  4. Persistance versionnée

    Le fichier modèle est écrit sous model/client_{id}/{type}_users_rating_model_v{n}.npz (jamais écrasé) et suivi par DVC (dvc_push).

  5. Trace MLflow

    Params, métriques et artefact sont journalisés dans MLflow ; si promu, l'alias "production" du Model Registry est réassigné de façon atomique. Une panne MLflow ne bloque jamais la promotion elle-même, déjà actée en Postgres.

06

API & SDKs

Toute requête s'authentifie via l'en-tête X-API-Key, résolu en client_id par get_current_client_id() — c'est ce qui garantit qu'aucune requête ne peut lire ou écrire les données d'un autre client, même en cas de nom de catalogue identique. Trois SDKs officiels partagent la même surface d'API.

sdk/python — likyly-recsys-sdk

RecsysClient (sync) et AsyncRecsysClient, basés sur httpx, Python 3.9+.

sdk/js — @likyly/recsys-sdk

Zéro dépendance (fetch natif) — Node 18+, bundlers front, ou <script type="module">. trackView() gère la liste de produits consultés en localStorage.

sdk/php — RecsysClient

Client PHP pour les stacks Laravel/Symfony/WordPress existantes.

08

Environnements & déploiement

Conteneur Docker

Dockerfile — image Python 3.11-slim, installe PyTorch CPU puis requirements-docker.txt, orchestré par Supervisor + Nginx.

Routage Nginx

nginx.conf — / vers l'app Solara (port 6060), /recsys-api/ vers l'API FastAPI (port 6061), le tout exposé sur le port 80.

Supervision des process

supervisord.conf démarre et redémarre automatiquement recsys-explore (Solara) et recsys-api (FastAPI/Uvicorn) côte à côte.

Séparation entraînement / service

Le réentraînement s'exécute en tâche d'arrière-plan dans le même process API (background_tasks) ; seul le fichier modèle versionné et sa ligne MLflow sont produits, le service continue de répondre pendant l'entraînement.
